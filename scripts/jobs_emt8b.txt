# emt8b: emt8's arms re-run with the head guarded and the handover made smooth.
#
#   python scripts/gpu_queue.py --jobs scripts/jobs_emt8b.txt
#
# SAME SPACE, SAME DATA, SAME BASE. Nothing about emt8 the space is in question
# -- src/emt/space.py, data/train-emt8 and data/val-emt8 are untouched, and the
# three arms resume from the identical checkpoint emt8 did. Two training
# settings change and nothing else. Read scripts/jobs_emt8.txt for where every
# numeric value came from; only the two deltas are argued here.
#
# WHY emt8 IS BEING REDONE. Its arms did not measure compression, they measured
# a runaway output head. The evidence, all from its own history.json:
#
#   zmax   base  1.65-2.17 for 2500 steps, sat_frac 0.000 throughout
#          arms  13.6 by step 3000, and linear 53.3 by 5500
#   sat    linear 0.221 -> 0.615 -> 0.693: at step 6000, 69% of the batch sat
#          past |z| = 2.5, where tanh' < 0.03. At |z| = 50 tanh' is zero in
#          float32, so most of the batch had no gradient at all.
#   h_abs  flat at 0.29-0.33 for every arm, so this was the head's weights
#          growing and not the trunk's features -- the distinction
#          train_encoder.py's own comment on last_z_absmax asks for.
#
# And the check that settles it. val_loss is loss_fn(xb, pred) unscaled, and the
# base arm was L1_STFT, so the base's val and the linear arm's val are the SAME
# FUNCTION on the same 991 clips:
#
#   base,   step 2500, never trained on it        0.3945
#   linear, step 6000, 3500 steps trained on it   0.6562
#
# The arm ended 66% worse at its own objective than the checkpoint it started
# from. That is not a bad minimum, it is a failed optimization, and no ranking
# taken across the three arms means anything -- linear sat 0.69, hyb 0.35, eps
# 0.30, so the ordering between them was an ordering of how fast each saturated.
#
# --------------------------------------------------------------------------
# CHANGE 1 of 2:  HEAD_HINGE=0  ->  1e-2
#
# The hinge is mean((|z|-1)+^2) on the RAW pre-activation, and --head-hinge's
# help already describes this exact failure: "The failing arms reach |z| of 60
# where reaching the box edge needs 1.47; that is runaway ... 1e-2 rather than
# 1e-3 because the penalty is exactly zero inside the box, so over-penalizing
# costs a healthy run nothing while under-penalizing wastes the run." emt8's
# linear arm reached 53.3. The value is taken from scripts/jobs_clamp.txt rather
# than invented.
#
# WHY THE HINGE AND NOT A DIFFERENT HEAD. softcap was measured -- head_probe,
# three bounds x two arms at 12k steps -- and paper/README.md records that
# linear landed at 0.0156-0.0170 whichever head was used, so it is safe but it
# is also not a fix here: train_encoder.py's own note says softcap "does NOT
# floor the total gradient", because the chain rule multiplies in
# (1 - tanh^2(z/c)), which still vanishes. softcap makes runaway harder to
# start; it cannot walk back from |z| = 50. The hinge can, because its gradient
# 2*lam*(|z|-1) GROWS with the excursion. Keeping HEAD_BOUND=tanh also keeps the
# head identical to emt7, raw7 and the quiet campaigns.
#
# WHY THE HEAD RAN AWAY AT ALL, which is what makes 1e-2 sufficient rather than
# hopeful. With HEAD_HINGE=0 the parameter loss was the only thing holding |z|
# inside the box: it penalizes |z_pred - z_true| with z_true in [-1, 1], so it
# pulls inward. param_w = 10*(1-f) reaches exactly 0 at f = 1, which emt8 hit at
# step 5000 -- and linear's zmax went 14.1 -> 53.3 in the next 500 steps. The
# restraint was removed by the schedule, on purpose, and nothing replaced it.
# The hinge is what replaces it, and unlike the parameter loss it carries no
# information about the answer, so the handover it is protecting stays a real
# handover.
#
# --------------------------------------------------------------------------
# CHANGE 2 of 2:  --param-hold-frac 0.125  ->  0.25
#
# emt8's base held spec_w at 0 through step 2500 (--param-hold-frac 1.0 of
# STEPS=2500), while its arms put the ramp start at 0.125 * 10000 = 1250. Those
# disagree by 1250 steps, so the arms resumed already a third of the way up:
#
#   f = (2501 - 1250) / 3750 = 0.334
#
# spec_w jumped 0 -> 0.334 and param_w dropped 10.0 -> 6.67 in a single step, at
# the full 3e-4 -- the arms are past the 2000-step warmup, and stage0_lr is
# cosine(st, 0, s0_end), counted from absolute 0, so a resume gets no warmup on
# the new objective however the --warmup-steps help reads. zmax went 2.05 ->
# 13.64 over the 500 steps that follow, and val_loss 0.3945 -> 1.047. The
# runaway starts HERE, 2500 steps before param_w reaches zero.
#
# 0.25 is 2500/10000: the hold now ends exactly where the base ends, so f = 0 at
# the resume and the crossfade is continuous from there. The ramp keeps its
# 0.375 duration, which puts its end at 6250 instead of 5000.
#
#   f = (step - 2500) / 3750,  0 at step 2500, 1.0 at step 6250
#
# Masuda & Saito's SHAPE is what transfers -- parameter-only, linear crossfade,
# spectral-only -- and it is preserved. Their boundaries as fractions (12.5%,
# ending at 50%) are not, because those assume the parameter-only phase is 12.5%
# of the run and here it is 25%. Matching the fractions while the base is 2500
# steps long is what produced the jump.
#
# A second benefit, unplanned but worth naming: LR is held at peak until step
# 6800 (span 10000-2000 = 8000, LR_HOLD 0.6 -> held 4800), so under emt8 the
# arms got 1800 steps of unanchored training at full rate before anything
# annealed. Now the crossfade finishes at 6250 and decay begins 550 steps later.
#
# --------------------------------------------------------------------------
# --ckpt-every 1000, down from the 5000 default. emt8 wrote its last checkpoint
# at step 5000 and the collapse was already complete there, so there was nothing
# to reach back to. 1000 costs a few seconds each.
#
# NOT COMPARABLE TO emt8's ARMS, which is the whole point. It IS comparable to
# emt8_pre, which it resumes from, and internally across its three arms.

# broken at their FIRST eval after the resume -- zmax 13.6 against the base's
# 2.05 -- so this does not need the run to finish to be answered:
#
#   python -m src.ddsp.monitor_sweep --root results/ddsp/emt8_pre results/ddsp/emt8b \
#       --metrics zmax sat spec_w
#
# At step 3000, spec_w should read 0.13 (not 0.47 -- that is change 2 landing),
# and zmax should still be single digits with sat near 0.000, as the base held
# for 2500 steps. If sat is above ~0.05 by step 3500 the hinge is not holding
# and 1e-1 is the next value; kill it rather than spending seven hours.
#
# Then the run proper:
#   python -m src.ddsp.monitor_sweep --root results/ddsp/emt8_pre results/ddsp/emt8b \
#       --metrics spec_w param g03 nmse ratio
#   python -m src.emt.perparam --root results/ddsp/emt8b --metric perr spread
#
# WHAT A CLEAN RUN LOOKS LIKE. The base reached ratio 0.18 and g03 0.2255 on
# parameter supervision alone. Any arm that ends above those did not benefit
# from its spectral loss, and that is now a statement about the loss rather than
# about the head. The handover collapse may well still be there -- DiffMoog's
# was real, and reproducing it is what this ladder is for -- but it has to
# happen with |z| inside the box before it counts.
