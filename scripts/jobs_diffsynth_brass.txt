# Brass-only real-audio training: does linear still win when the target class is
# fixed, rather than averaged over all of NSynth?
#
#   python scripts/gpu_queue.py --jobs scripts/jobs_diffsynth_brass.txt
#
# THE HYPOTHESIS AND WHERE IT CAME FROM, stated plainly because the provenance
# decides how the result may be reported. Evaluating the existing all-NSynth
# arms per instrument class gave, on brass_acoustic under log-mfcc normalised by
# the within-class spread:
#
#   real_magx_halfw  0.4367     linear
#   real_hybridx     0.4426     hybrid
#   real_logx_halfw  0.4912     log
#
# so linear wins by 0.0059 on 82 clips. That is a HYPOTHESIS drawn from
# jointly-trained models, and these runs are its test under class-specific
# training. It is not a result that may be quoted as confirming itself: the
# class was chosen because linear won there, so the joint-trained margin cannot
# also serve as evidence. What is being asked is whether the sign survives a
# different training regime.
#
# WHY BRASS AND NOT A MEASURED CRITERION. Four audio statistics were tested
# against the 19-class margin -- bin share below four thresholds, energy share
# below four thresholds, spectral flatness, effective spectrum size. The best
# was flatness at r = +0.473, p = 0.027 against a Bonferroni threshold of 0.005,
# with Spearman only +0.307. Nothing predicts which loss wins from the audio, so
# the class cannot be selected on mechanism and this one rests on two weaker
# legs: linear wins there in the joint-trained table, and brass is conceptually
# reachable -- sustained, strongly harmonic, no inharmonicity, no strike
# transient, which is close to what a harmonic oscillator through a lowpass can
# actually produce. Its fit of 0.437 is the best of the four classes where
# linear wins.
#
# THE DATA. 12605 brass_acoustic files pulled from nsynth-train by streaming the
# archive through tar with a wildcard, so the 22 GB was never stored. The ID
# directory is symlinks to 12288 of the h2of set, because data.py:92 draws
# len(id_dat) samples from the ood set WITHOUT replacement and 20000 from 12605
# raises. ID is used only for val_id metrics here -- train_type is ood -- so
# shrinking it does not touch training, but val_id numbers are not comparable to
# the existing table.
#
# All three arms branch from their own pre_* at latest.ckpt, epoch 199 / step
# 50000, verified identical across the three. That is the same branch point the
# existing real_* arms used, so these drop beside them.
#
# log_grad=false. It logs gradient histograms every step and is what filled the
# disk: 9 GB of event files across the earlier runs, 1.6 GB for ploss alone
# against 97 MB of its checkpoints. scalars.csv carries everything
# monitor_diffsynth reads.
#
# ~79 s/epoch at 154 batches, so 200 epochs is about 4.4 h per arm.

ID_DIR=external/diffsynth/data/h2of_12k OOD_DIR=external/diffsynth/data/nsynth-brass RESUME=pre_magx_halfw scripts/ds_run.sh real_br_magx_halfw resume_real "{gpu}" trainer.checkpoint_every_n_epochs=50 model.log_grad=false model.sw_loss.log_mag_w=0 model.sw_loss.power=1 schedule.sw_w.end_v=0.5
ID_DIR=external/diffsynth/data/h2of_12k OOD_DIR=external/diffsynth/data/nsynth-brass RESUME=pre_hybridx    scripts/ds_run.sh real_br_hybridx    resume_real "{gpu}" trainer.checkpoint_every_n_epochs=50 model.log_grad=false model.sw_loss.power=1 model.sw_loss.log_eps_v=1e-2
ID_DIR=external/diffsynth/data/h2of_12k OOD_DIR=external/diffsynth/data/nsynth-brass RESUME=pre_logx_halfw scripts/ds_run.sh real_br_logx_halfw resume_real "{gpu}" trainer.checkpoint_every_n_epochs=50 model.log_grad=false model.sw_loss.power=1 model.sw_loss.log_eps_v=1e-2 model.sw_loss.mag_w=0 schedule.sw_w.end_v=0.5
